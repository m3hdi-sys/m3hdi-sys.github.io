Déploiement & Automatisation d'une Infrastructure Multi-Serveurs Conteneurisée

Conception d'un cluster de conteneurs Linux légers (LXC) sous Proxmox VE piloté à distance via une interface ChatOps (Bot Discord en Python).

1. Virtualisation & Micro-Architecture LXC (Proxmox VE)

Chaque instance applicative est isolée dans son propre conteneur Debian/Ubuntu avec adressage IPv4 statique dédié :

• CT 109 (192.168.0.50/24) : Nœud de contrôle & Bot Discord d'administration (bot-minecraft.service) • CT 107, 108, 110, 111 (192.168.0.51 à .54/24) : Instances applicatives isolées (minecraft-bedrock.service) • Administration depuis l'hôte Proxmox : pct exec, pct enter, pct push

2. Réseau, Clés SSH Asymétriques & Tunneling TCP/UDP

Le conteneur d'administration (CT 109) dialogue avec les conteneurs cibles via SSH par clés asymétriques sans mot de passe. L'exposition publique sécurisée (contournement CGNAT sans ouverture de ports FAI) est assurée par des tunnels TCP/UDP Playit.gg.

3. Automatisation ChatOps (Python Asyncio) & Parsing Journalctl

Développement d'un Bot Discord (discord.py) exécuté dans un environnement virtuel isolé (venv) :

• Commandes Slash (/mc, /maj) & composants interactifs (Boutons, Menus, Modals, Embeds temps réel) • Exécution asynchrone (asyncio.create_subprocess_shell) des ordres systemctl start/stop/restart via SSH • Script update_mc_players.py : Parsing Regex de journalctl sur la dernière heure pour extraire les sessions actives • Calcul d'uptime dynamique via ActiveEnterTimestamp systemd et extinction automatique en cas d'inactivité • Sauvegardes automatisées : Script Bash (backup-world.sh) générant des archives .tar.gz listées dans Discord
[ RAPPORT TECHNIQUE ] : CONFIGURATION_VPN_SITE_TO_SITE_IPSEC.pdf

Compte-rendu : VPN Site-to-Site IPsec (Cisco)

OBJECTIF : Interconnecter deux réseaux locaux distants (LAN A 192.168.1.0/24 et LAN C 192.168.3.0/24) de manière sécurisée via un tunnel chiffré traversant un réseau WAN non sécurisé (Internet/ISP).

1. Infrastructure, Module HWIC-2T et Plan d'adressage

L'architecture repose sur trois routeurs Cisco 1941 équipés de modules séries HWIC-2T. Le routeur R2 simule l'opérateur WAN (ISP), tandis que R1 et R3 sont les passerelles de sécurité des deux sites distants :

[PC-A : 192.168.1.3] ─── (Gi0/0: 192.168.1.1) [Routeur R1] (Se0/0/0: 10.1.1.1) │ Liaison Série WAN (HWIC-2T) │ (Se0/0/0: 10.1.1.2) [Routeur R2 - ISP] (Se0/0/1: 10.2.2.1) │ Tunnel Chiffré IPsec ESP │ [PC-C : 192.168.3.3] ─── (Gi0/0: 192.168.3.1) [Routeur R3] (Se0/0/0: 10.2.2.2)

Vérification de l'état des interfaces UP/UP sur l'ensemble de l'infrastructure :

R1# show ip interface brief Interface IP-Address OK? Method Status Protocol GigabitEthernet0/0 192.168.1.1 YES NVRAM up up Serial0/0/0 10.1.1.1 YES NVRAM up up R2# show ip interface brief Interface IP-Address OK? Method Status Protocol Serial0/0/0 10.1.1.2 YES manual up up Serial0/0/1 10.2.2.1 YES manual up up R3# show ip interface brief Interface IP-Address OK? Method Status Protocol GigabitEthernet0/0 192.168.3.1 YES NVRAM up up Serial0/0/0 10.2.2.2 YES NVRAM up up

2. Activation de la licence SecurityK9 & Configuration IPsec

Activation du package technologique cryptographique securityk9 requis sur Cisco ISR 1941, puis configuration des phases IKE Phase 1 (ISAKMP AES, Pre-shared key, Diffie-Hellman) et Phase 2 (transform-set et crypto map) :

R1(config)# license boot module c1900 technology-package securityk9 ACCEPT? [yes/no]: yes % use 'write' command to make license boot config take effect on next boot ! --- Phase 1 (ISAKMP) & Phase 2 (IPsec) --- R1(config)# crypto isakmp policy 10 R1(config-isakmp)# encryption aes R1(config-isakmp)# authentication pre-share R1(config-isakmp)# group 2 R1(config)# crypto isakmp key SECRET_VPN_KEY address 10.2.2.2 R1(config)# crypto ipsec transform-set VPN-SET esp-aes esp-sha-hmac R1(config)# crypto map VPN-MAP 10 ipsec-isakmp R1(config-crypto-map)# set peer 10.2.2.2 R1(config-crypto-map)# set transform-set VPN-SET R1(config-crypto-map)# match address 101

3. Validation et Preuve de Chiffrement (Encapsulation / Décapsulation)

Test de connectivité (Ping ICMP) entre PC-A (192.168.1.3) et PC-C (192.168.3.3) et analyse des compteurs de sécurité IPsec :

R1# show crypto ipsec sa interface: Serial0/0/0 local ident (addr/mask/prot/port): (192.168.1.0/255.255.255.0/0/0) remote ident (addr/mask/prot/port): (192.168.3.0/255.255.255.0/0/0) current_peer 10.2.2.2 port 500 PERMIT, flags={origin_is_acl,} #pkts encaps: 7, #pkts encrypt: 7, #pkts digest: 0 #pkts decaps: 6, #pkts decrypt: 6, #pkts verify: 0 #send errors 1, #recv errors 0

✓ Succès : #pkts encaps: 7 | #pkts decaps: 6. Le tunnel chiffré IPsec est pleinement opérationnel.
